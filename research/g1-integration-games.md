# Research: Per-game automation/API surface and Linux feasibility for a scripted client (no headset, no controllers)

## Summary

All 13 candidate titles run acceptably on Linux (12 via Proton; Half-Life: Alyx has a native Vulkan build) — the Linux question is largely settled, because nearly every report assumes a real streaming headset (ALVR/WiVRn/Monado) rather than a synthetic one. The real blocker is the headset: OpenXR runtimes such as SteamVR refuse to initialise when no HMD is detected, so the game must either (a) have a desktop/no-HMD mode, or (b) be fed poses through a driver-level hack (SteamVR null driver + `TrackingOverrides`, OpenVR-InputEmulator, a custom driver, or a Monado driver). Only **VRChat** (official OSC input + OSC trackers) and **Resonite** (ResoniteLink + native Linux headless) expose a sanctioned, EAC-safe path for an external process to drive head/hand pose and movement; **Beat Saber** has by far the richest mod/replay ecosystem but no supported pose-injection path; several titles (Job Simulator, I Expect You To Die, Walkabout, Pistol Whip) have no usable API at all.

## Notes

### 1. Linux status — mostly a solved problem, but every report assumes real hardware
Beat Saber is Platinum on ProtonDB (258 reports; Proton 9.0-3 recommended) \[1\]\[2\], with VRDB reports across SteamVR, Monado, ALVR and WiVRn, including modded play via BSManager \[3\]. Verified quirks: modded launches need `WINEDLLOVERRIDES="winhttp=n,b"` or `STEAM_COMPAT_CLIENT_INSTALL_PATH`, and Monado/WiVRn needs `OXR_PARALLEL_VIEWS=0` on 1.40.8 \[3\]. A historical OpenXR crash on the Unity branch was fixed in Proton 9 and a SteamVR beta [3a: https://github.com/ValveSoftware/Proton/issues/6638]. Superhot VR \[4\], Pistol Whip \[38\]\[39\], Boneworks \[36\]\[37\], BONELAB \[33\], Blade & Sorcery \[17\]\[18\] and Gorilla Tag \[51\] all have working community reports, mostly via ALVR/WiVRn. Walkabout works but has a persistent right-eye distortion above 100% render scale (open SteamVR-for-Linux bug; WiVRn unaffected per reporters) \[24\]\[25\]. I Expect You To Die works but has documented OpenXR-init and controller action-manifest problems \[14\]. Eleven Table Tennis has contradictory reports (works on GE-Proton9.7; controllers disappear after opening the Steam menu; earlier builds crashed) \[40\]\[41\]. Half-Life: Alyx shipped an **official native Linux + Vulkan build** with Workshop tools \[43\], so it is the only native-Linux title here; VRDB notes the native build still needs library workarounds while the Proton build often behaves better \[44\].

### 2. Headset requirement is the real constraint; synthetic-HMD support is fragile
OpenXR documentation is explicit: "Runtimes such as SteamVR will refuse to even initialise OpenXR if no HMD is detected" — `xrCreateInstance` fails [79: https://openxr-tutorial.github.io/setup/creating_an_instance.html]; known SteamVR versions crashed outright instead of returning an error [80: https://github.com/KhronosGroup/OpenXR-SDK-Source/issues/384]. Unity's OpenXR plugin then loops restart errors with no HMD [81: https://issuetracker.unity.com/issues/14717/openxr-error-looped-when-no-hmd-is-present]. Therefore a synthetic HMD must be supplied *below* the game:
- **SteamVR null driver**: set `requireHmd=false`, `forcedDriver="null"`, `activateMultipleDrivers=true` and enable the null driver to run SteamVR with no headset [82: https://github.com/username223/SteamVRNoHeadset]. **Uncertain / flag**: SteamVR later added a "No headset detected" gate that blocked controller pairing in this configuration (2020 report) [83: https://steamcommunity.com/app/250820/discussions/2/1732087824985301933/]; I found no current, Linux-specific confirmation that this still works.
- **SteamVR `TrackingOverrides`**: a custom driver can override poses for `/user/head`, `/user/hand/left`, `/user/hand/right` "at the system's raw pose level", which is the only route that feeds SteamVR's forward-prediction engine correctly — Valve explicitly notes that overriding poses inside the app (WaitGetPoses) is *not* equivalent [84: https://github.com/ValveSoftware/openvr/wiki/TrackingOverrides]. Custom drivers follow the documented `IServerTrackedDeviceProvider` sample [85: https://github.com/ValveSoftware/openvr/blob/09240643/samples/drivers/drivers/tutorial/README.md].
- **OpenVR-InputEmulator** creates virtual controllers, redirects/sets poses via offsets, and exposes a shared-memory client API for external programs — but it hooks the Lighthouse driver; Valve engineers warn hook drivers are "a major source of instability" and break on driver API changes [86: https://github.com/sharkyh20/OpenVR-InputEmulator · 87: https://github.com/ValveSoftware/openvr/issues/1187]. Windows-era, unmaintained — **uncertain on Linux**.
- **callum1h3/SteamVR-Unity-Integration** replaces `driver_null` so an external process writes HMD/left/right pose pointers, claiming "you can bypass Anti-Cheat on games because Anti-Cheat does not protect SteamVR itself" and citing Gorilla Tag pose-spoofing as its own example [88: https://github.com/callum1h3/SteamVR-Unity-Integration]. Treat the anti-cheat-bypass claim as the **author's assertion, not verified**; the Gorilla Tag discussion shows server-side detection/bans for exactly this \[55\]\[56\]\[57\].
- **Monado** (the realistic Linux-native option) ships a simulated driver, a remote driver, and a **qwerty driver** (keyboard/mouse HMD + controllers), plus `XR_MND_headless` [89: https://monado.freedesktop.org/ · 90: https://redstrate.com/blog/2023/11/using-openxr-without-real-hardware/]. It also documents writing your own `xrt_device` driver [91: https://monado.pages.freedesktop.org/monado/writing-driver.html], which is the clean way to feed G1-derived poses over IPC. Caveat: the remote driver is GUI-only and Monado's simulated driver is deliberately non-configurable at runtime \[90\].
- **xr-sim** is a deterministic, scripted-input, headless OpenXR runtime — but **Windows x86/x64 only** [92: https://github.com/phunkaeg/xr-sim], as is fholger's OpenXR-Simulator [93: https://github.com/fholger/OpenXR-Simulator]; neither is usable on a Linux host.
- **Proton ↔ host runtime**: Proton 9+ needs `PRESSURE_VESSEL_IMPORT_OPENXR_1_RUNTIMES=1` to see the host OpenXR runtime, and OpenVR games under Proton need xrizer or OpenComposite [94: https://vronlinux.org/docs/fossvr/wivrn/ · 95: https://www.protondb.com/app/438100]. Consequences: an OpenVR-era title (e.g. Blade & Sorcery per community reports \[29\]) reaches Monado through a translation layer whose binding gaps are already documented, which adds failure modes to any pose injection scheme.

### 3. Game-state and contact-event APIs
**Beat Saber** is the standout: multiple BSIPA/BepInEx mods expose live game state over local sockets — `beatsaber-http-status` (ws://localhost:6557, incl. a `noteSpawned` event with per-note data) \[10\], BSDataPuller (ws://localhost:2946, `MapData`/`LiveData` incl. per-note cut results) \[11\], SocketSaber (localhost TCP, e.g. port 9999) \[12\] and BS_AnotherStatusSocket (ws://localhost:13339, full level metadata incl. note/bomb/wall counts and modifiers) [12a: https://git.gay/TheBlackParrot/BS_AnotherStatusSocket]. Replay formats already encode exactly the (head, left hand, right hand) pose stream this project needs: BSOR (BeatLeader, per-frame head + left/right position & quaternion, plus per-note cut geometry) \[8\] and the legacy ScoreSaber format (same frame structure) [8a: https://github.com/zipsegv/BS-Open-Replay]. That means a Beat Saber target can be formulated as *offline* trajectory generation (as CyberRamen does) plus a realtime pose feed \[8\]\[9\]. **VRChat** gives only parameter/input/tracker level state via OSC — no world-specific object data unless the world is Udon-authored with matching parameters \[63\]\[64\]. **Resonite** is fully introspectable and writable through ResoniteLink, including continuous realtime updates \[75\]. **Blade & Sorcery** scripted mods (C# + Harmony) can read/write anything, but are per-game-version \[30\]\[31\]. **Half-Life: Alyx** VScript Lua addons can query entities and player state \[48\]\[49\]. No state API was found for Superhot VR, Walkabout, IEYTD, Job Simulator, Pistol Whip or Eleven — **negative search result, not proof of absence**.

### 4. Anti-cheat
Only **VRChat** ships a kernel-level anti-cheat: EAC, live since 2022.2.2 \[69\]. VRChat states it works on Proton/Steam Deck (desktop), and Linux users confirm VR mode works via Monado/WiVRn, sometimes needing retries or Proton-RTSP \[69\]\[70\]\[58\]\[59\]. Crucially, EAC "prevents the use of client modifications" and blocked injection-based tools (Virtual Desktop's Oculus injection) \[69\] — so DLL injection is out, while **network-level OSC is untouched**. **Gorilla Tag** uses server-side anti-cheat plus behavioural enforcement (bans for mods in public *and* private lobbies; ADB long-arms/fly blocked Oct 2024) \[55\]\[56\]\[57\]. No anti-cheat was found for Beat Saber, Blade & Sorcery (aggregator states "None") \[2\]\[17\], Superhot VR, Walkabout, IEYTD, Job Simulator, Pistol Whip, BONELAB, Boneworks or Alyx — **unverified for Eleven Table Tennis**, which is online-multiplayer and therefore likely governed by ToS rather than an AC module.

### 5. Practical recommendation for this project
Constraint: body has no neck joint, so HMD orientation ≡ torso orientation, and only three tracked points (torso + 2 wrists) plus a 2D velocity command are available.
1. **VRChat** — closest fit. OSC trackers accept world-space position + **euler angles** for `head` and up to 8 body trackers, and head position "will be fully aligned per frame" while head rotation yaw "slowly lerp[s]" (with a 300 ms single-message / 10 s timeout rule) \[63\]\[64\] — i.e. translation is frame-exact and orientation is smoothed, which matters for control-loop design. `/input/*` axes give locomotion and buttons \[62\], and OSC does not conflict with EAC \[69\].
2. **Resonite** — ResoniteLink plus the officially supported Linux/ARM headless client means the whole session can be scripted server-side, no headset at all \[73\]\[74\]\[75\].
3. **Beat Saber** — best mod/telemetry ecosystem and an existing AI-play precedent, but pose injection requires one of the driver-level hacks in §2, all of which are either Windows-oriented, unmaintained, or in Monado's case require writing a custom driver.
4. **Half-Life: Alyx** — native Linux, flat NoVR mod proves non-HMD operation, and VScript gives in-game scripting \[43\]\[45\]\[48\].
5. Deprioritise Job Simulator, I Expect You To Die, Walkabout, Pistol Whip, Eleven, Superhot: no API found, so all interaction would have to be driver-level pose spoofing plus game-specific reverse engineering.

### Explicit uncertainty register
- Whether SteamVR's null-driver configuration still permits HMD-less sessions (and controller pairing) on current SteamVR-for-Linux builds — **unverified**; only a 2020 community report of a regression \[83\].
- Whether OpenVR-InputEmulator or callum1h3's null-driver replacement can be built/used on Linux — **unverified**; both are presented as Windows projects, and 88's anti-cheat-bypass claim is unverified.
- No confirmed report of any of these 13 titles successfully running and being driven *headless* with a synthetic HMD (i.e. without any streaming headset in the loop); ProtonDB reports like Walkabout's "launches fine and goes to the menu without a VR headset attached" \[6\] are ambiguous and should not be read as a working headless mode.
- Anti-cheat presence for Eleven Table Tennis, Superhot VR, Walkabout, Pistol Whip, IEYTD, Job Simulator, BONELAB, Boneworks, Alyx: "none found" = no evidence located, not confirmed absence.
- All ProtonDB/LVRA "works" reports involve a real headset; they establish game-side Linux viability only.
