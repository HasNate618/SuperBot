# Research: Reconciling the VR game's world with the MuJoCo world (G1 + Monado remote driver)

## Summary

No published system does exactly this — a *physically simulated* humanoid closing the loop through a *closed commercial VR game*. The three adjacent solved problems are (a) avatar telepresence between dissimilar spaces, where walk-in-place plus game-driven translation/teleport is the standard reconciler; (b) humanoid VR teleoperation, where a pretrained RL whole-body policy is used as an API that accepts arbitrary upper-body poses *and* a velocity command (HOMIE), which is essentially your architecture; and (c) bilateral telelocomotion, where a virtual reference model is synchronised to the robot rather than the operator. Coordinate conversion is a fixed rotation (OpenXR LOCAL: +Y up, −Z forward, metres, yaw-locked → MuJoCo: Z-up, X forward, Y left, `wxyz` quaternions). Infeasible targets are handled by QP retargeting with clamping/windup guards, never by refusing. There is **no standard channel** for game contact events: only haptic output, pixel inference, or game mods.

## 1. Locomotion divergence

1. **Walk-in-place + game-driven translation is the established reconciler.** The clearest precedent is full-body avatar telepresence between dissimilar rooms: when the user's pelvis speed exceeds a threshold, the avatar switches to **Walk-In-Place** (pose mimics the user, position/orientation frozen) and, when the user stops, the avatar is **teleported** to a re-computed optimal placement. The stated benefit is that WIP "preserves the context of moving while hiding the user's actual moving path" — exactly your divergence problem, solved by never mapping physical displacement to virtual displacement ([arXiv 2103.04380](https://ar5iv.labs.arxiv.org/html/2103.04380)).
2. **WIP foot-tapping interfaces for humanoid robots already exist.** A foot-tapping WIP interface generated high-level movement commands for a remotely controlled humanoid; 8 participants tracked a leading target at <1 m/s with **average tracking error 0.47 m** ([IEEE Humanoids 2020](https://dl.acm.org/doi/10.1109/HUMANOIDS47582.2021.9555768)). Notably comparable in magnitude to your measured 0.475 m/5 s drift — a useful sanity scale for "acceptable" open-loop error.
3. **iFeel Walking (iCub, ANA Avatar XPRIZE)** used Vive foot/waist trackers plus instrumented shoes: step-in-place *triggers* robot motion, and speed is modulated by stepping frequency. It also had a "chaperon" safety zone that stops mapping operator motion when the operator leaves a safe area — a design worth copying for your interface ([ICRA 2023 Avatar Workshop](https://www.ais.uni-bonn.de/ICRA2023AvatarWS/contributions/ICRA_2023_Avatar_WS_Sartore.pdf)). Cautionary note: the robot fell in the finals after hitting a pillar, attributed to poor depth perception through the headset.
4. **Matching achieved velocity to commanded velocity is usually done on the *human* side, not the robot side.** The Science Robotics bilateral telelocomotion work applies feedback forces to the operator "proportional to the relative velocity between human and robot", speeding the human up or dragging them back to enforce dynamic similarity ([Sci. Robotics aav4282](https://www.science.org/doi/10.1126/scirobotics.aav4282)). Follow-ups abstract the operator into a virtual Hybrid-LIPM reference and use a **damped-least-squares fit of swing-foot z** so the pilot and robot touch down synchronously, controlling speed 0.0–0.3 m/s ([arXiv 2307.10533](https://arxiv.org/html/2307.10533v2)); the earlier framework walked 1.28 m in 10 steps at 0.36 m/s ≈ 40% of average human walking speed ([arXiv 2209.06964](https://arxiv.org/pdf/2209.06964)).
   → **Implication for you:** your Playground policy already gives you a measured 0.516/0.5 = 1.03 velocity gain at 0.5 m/s. The cheapest reconciler is to **close the velocity loop on the robot side**: command the game a thumbstick value derived from *achieved* base velocity, so the game's camera translation is driven by the robot's actual motion rather than the reverse. That inverts the usual dependency and needs no base teleporting.
5. **Base reset/sync from the game is mechanically easy but perceptually disruptive.** In MuJoCo you can write the free-joint `qpos` indices directly and call `mj_forward` (qpos has higher dimensionality than qvel for free joints, so quaternion algebra applies), or convert the root `body` to a **mocap body** and write `mjData.mocap_pos`/`mocap_quat` — documented explicitly as the mechanism "to set the positions and orientations of static bodies in real-time, for example when streaming 6D poses from a motion-capture device" ([MuJoCo simulation docs](https://mujoco.readthedocs.io/en/stable/programming/simulation.html); maintainer guidance in [mujoco#1395](https://github.com/google-deepmind/mujoco/issues/1395)). **Pitfall:** teleporting the base injects a step change in `qvel`, which lands directly in your policy's `linvel(3)`/`gyro(3)` observations and can destabilise it. Prefer rate-limited or footstep-aligned correction.
6. **Redirected walking / impossible spaces are largely irrelevant to a robot.** RDW gains (rotation, translation, curvature, bending) and impossible spaces (rooms overlapped up to 56% for small rooms, 31% for 9.14 m rooms) all exist to stay *below human perceptual detection thresholds* ([15 Years of RDW](https://www.cs.purdue.edu/cgvlab/courses/490590VR/notes/VRLocomotion/15YearsOfRedirectedWalking.pdf); [RDW taxonomy survey](https://arxiv.org/html/2505.16011)). A robot feels no cybersickness, so you can violate these thresholds freely — the binding constraints become game semantics (does the game's locomotion have collision/inertia?) rather than perception. **Uncertainty: high** — this is my inference, not a finding in the literature.
7. **Gait-quality baselines from omnidirectional treadmills.** ODT walking is ~65% slower than overground with shorter steps; turning requires more steps and is slower ([JNER 2023](https://link.springer.com/article/10.1186/s12984-023-01286-6)), and one controlled study found ODT reduced walking performance and increased simulator sickness vs. real walking ([TU Wien 2024](https://repositum.tuwien.at/bitstream/20.500.12708/209746/1/Wang-2024-Investigating%20Walking%20Performance%20and%20Experience%20with%20Different...-vor.pdf)). Useful as an expectation-setting benchmark for how much fidelity "physical walking in VR" typically retains.
8. **Directly relevant architectural precedent:** a Unity framework with a PICO Neo3 headset controlling a **Unitree G1** maps raw controller input into *chassis velocity, arm IK targets, and gripper commands* — with an explicit "chassis speed" action dimension ([arXiv 2604.16903](https://arxiv.org/html/2604.16903v1)). ⚠️ **Uncertainty: high** — this arXiv ID is anomalous (year-2026 style); verify the ID resolves before citing.

## 2. Coordinate frames

1. **OpenXR is right-handed Cartesian, metres, quaternion `(x,y,z,w)`, pose = orientation then position; axis meanings are documented *per space* rather than globally** ([OpenXR 1.0 spec §2.18](https://registry.khronos.org/OpenXR/specs/1.0-khr/html/xrspec.html)).
2. **Reference spaces and their exact conventions** ([XrReferenceSpaceType 1.1](https://registry.khronos.org/OpenXR/specs/1.1/man/html/XrReferenceSpaceType.html)):
   - `VIEW`: +Y up, +X right, −Z forward; **not gravity-aligned**.
   - `LOCAL`: world-locked origin, **gravity-aligned to exclude pitch and roll**, +Y up/+X right/−Z forward. Locks both initial position *and* initial orientation. **This is your yaw-only rig**: pitch/roll are removed by construction; yaw is whatever the calibrated zero was.
   - `LOCAL_FLOOR`: as LOCAL but origin at estimated floor level.
   - `STAGE`: origin on the floor at the rectangle centre, +Y up, X/Z aligned with the rectangle edges — closest to MuJoCo's world frame modulo the axis permutation.
3. **Tracking-loss semantics matter for a robot.** When a space experiences tracking loss relative to LOCAL, the runtime *should keep providing inferred or last-known pose while clearing the `TRACKED` bit* and keeping `POSITION_VALID` ([XR_REFERENCE_SPACE_TYPE_LOCAL](https://registry.khronos.org/OpenXR/specs/1.1/man/html/XR_REFERENCE_SPACE_TYPE_LOCAL.html)). Your pose client must read the valid/tracked bits; a "frozen" pose is otherwise indistinguishable from a stationary robot.
4. **MuJoCo is right-handed, Z-up (gravity `0 0 -9.81`, "in the default world orientation the Z-axis points up"), X forward, Y left, with scalar-first (`wxyz`) quaternions** ([MuJoCo XML reference](https://mujoco.readthedocs.io/en/3.4.0/XMLreference.html); [mink MuJoCo basics](https://kevinzakka.github.io/mink/tutorial/mujoco_basics.html)). **Concrete pitfalls:** (i) **quaternion order differs** — OpenXR is `x,y,z,w`, MuJoCo is `w,x,y,z`; (ii) **6D velocities are mixed-frame in MuJoCo** — linear velocity in *world* frame, angular velocity in *body* frame, and converting to other Jacobian conventions (e.g. Pinocchio `LOCAL_WORLD_ALIGNED` vs body) requires explicit handling ([mink](https://kevinzakka.github.io/mink/tutorial/mujoco_basics.html)); (iii) MJCF `eulerseq` defaults to `"xyz"` and URDF `rpy` corresponds to MJCF `"XYZ"` — a silent trap if you convert the G1 URDF ([XML reference](https://mujoco.readthedocs.io/en/3.4.0/XMLreference.html)).
5. **Monado remote driver specifics.** The packet is `r_remote_data { uint64_t header; r_head_data head; r_remote_controller_data left, right; }`, header magic `mndrmt3\0`. `r_head_data.center` is documented as "the center of the head, **in OpenXR terms the view space**", with per-view FOV and per-view pose *relative to* `center` ([r_interface.h source](https://monado.pages.freedesktop.org/monado/r__interface_8h_source.html)). The hub creates devices with `XRT_POSE_IDENTITY` and sets `xrt_tracking_origin::initial_offset`, so **the injected pose is in OpenXR view-space convention and the game will then apply its own reference-space transform**. You must invert whichever `XrReferenceSpaceType` the game requests (LOCAL vs STAGE differ by a floor offset and a yaw) or you will get persistent yaw/height bias. ⚠️ `r_interface.h` carries a **"Copyright 2026, NVIDIA CORPORATION"** line alongside Collabora — the upstream interface may have changed recently; diff your Monado revision against the published docs.
6. **No documented haptic/force field exists in the remote packet** — the controller struct carries pose, linear/angular velocity, `hand_curl\[5\]`, trigger, squeeze, `squeeze_force`, thumbstick, `trackpad_force`, trackpad, and 11 button/touch booleans, plus `hand_tracking_active`/`active` ([r_interface.h source](https://monado.pages.freedesktop.org/monado/r__interface_8h_source.html)). ⚠️ This is the *debugger→hub* direction; I did not verify a hub→client channel, and `r_remote_connection_write_one` exists.

## 3. Infeasible targets

1. **The dominant published answer is "retarget to the nearest feasible configuration", not clamp, not refuse.** SEIKO formulates whole-body retargeting as a QP that rewrites Cartesian commands into a feasible posture + contact wrenches, and explicitly targets "far-reaching tasks" and "commanding the end-effector out of reach" ([SEIKO paper](https://arxiv.org/html/2312.16465v3), [PDF](https://hucebot.github.io/seiko_controller_website/resources/SEIKO_Controller.pdf), [feasibility-retargeting summary](https://exa.ai/library/publication/ylz9v3cn0xp)).
2. **Three specific mechanisms you should copy:**
   - **Anti-windup clamping around the *achievable* pose, not the commanded pose.** SEIKO keeps a reference pose `X_ref` and clamps it within a radius of the *target* pose "to prevent the reference pose from windup when the retargeted motion is saturated by the feasibility constraints."
   - **Time-optimal bang-bang replanning** to bound velocity and acceleration between timesteps, plus low-pass filtering — explicitly "to further enhance robustness against aggressive motions and network communication jitter."
   - **Admittance velocity with deadband + output clamping on linear and angular norm**, to reject peak forces and inertial effects.
3. **Explicit limitation to respect:** SEIKO "inherently relies on the quasi-static assumption and is unsuitable for highly dynamic motions" ([SEIKO paper](https://arxiv.org/html/2312.16465v3)). Your G1 policy is a dynamic locomotion policy; a quasi-static retargeting filter layered on top will fight it.
4. **Stability-aware retargeting** adjusts contact points and posture using a centroidal stability margin gradient to avoid torque saturation and slipping under teleoperation setpoints; higher stability margin empirically correlates with impulse resilience and joint torque margin ([stability-aware retargeting](https://exa.ai/library/publication/ljzrsztspjb)).
5. **Out-of-reach / self-collision references are typically *silently overridden*.** A CBF-WBC makes the MIT Humanoid's hand "deviate from an infeasible reference trajectory to avoid self-collisions", and the authors flag the open problem: "if the footstep planned by LMPC is truly infeasible, the **LMPC planner should be informed accordingly**" ([CBF-WBC self-collision](https://exa.ai/library/publication/0hdrnxc56bd)). **This is the key interface lesson for you:** your VR-game bridge must be told when its target was infeasible, or the game's HMD pose will silently diverge from the robot's torso with no feedback path.
6. **Filtering as a convex QP** generalises this: safety (CBF) and passivity constraints combined into one QP that minimally modifies human + feedback input ([safety & passivity filter](https://ar5iv.labs.arxiv.org/html/2102.08630)), and for delay specifically, an **adaptive safety margin proportional to estimated RTT × velocity** avoids the over-conservatism of worst-case bounds — directly applicable since your pose stream is networked ([MPC-CBF adaptive margins](https://arxiv.org/html/2403.18650v1)). A hierarchical ISSf-CBF whole-body filter covering joint limits, self-collision, obstacle avoidance and workspace boundaries, validated in teleoperation, is the most complete recent humanoid-specific option ([SafeWBC](https://kwlee365.github.io/SafeWBC-Website/)).
7. **Published architecture closest to yours — use it as the design template.** HOMIE trains an RL policy whose command interface *is* `[v_x, ω_yaw, h_torso]` plus arbitrary upper-body joint poses, using an "upper-body pose curriculum" so balance survives continuously changing arm poses, a height-tracking reward for squatting, and symmetry for data efficiency. It deliberately avoids IK by using an isomorphic exoskeleton. ([HOMIE paper](https://arxiv.org/html/2502.13013), [project page](https://homietele.github.io/)). VIRAL uses HOMIE as its WBC "API layer", noting the action space is thereby "limited to a safe and reliable region of humanoid motions" ([VIRAL](https://arxiv.org/html/2511.15200)). **This is the strong version of your answer to Q3:** don't filter infeasible pose targets at runtime — *train the policy with an upper-body pose curriculum* so the feasible set is large and the policy handles excess internally.
8. **Clamping bounds measured in a G1 VR adapter** (informative, but see the ID caveat in §1.8): arm IK targets clamped to `x∈[-0.08,0.15], y∈[-0.08,0.35], z∈[-0.15,0.08]` m per hand, wrist rotation limited to ±45° per axis, and IK targets updated only while a clutch button is held "to prevent abrupt arm jumps" ([arXiv 2604.16903](https://arxiv.org/html/2604.16903v1)). The clutch-plus-relative-delta pattern is probably what you want, since your game poses will occasionally be garbage.

## 4. Force/contact loop

1. **The only *standard* game→XR channel is haptic output, and it is game→runtime, not runtime→game.** `xrApplyHapticFeedback` fires an `XR_ACTION_TYPE_VIBRATION_OUTPUT` action with `XrHapticVibration { duration(ns), frequency(Hz), amplitude(0..1) }`; the runtime may clamp parameters and may simply ignore the request if no appropriate device exists ([xrApplyHapticFeedback](https://registry.khronos.org/OpenXR/specs/1.1/man/html/xrApplyHapticFeedback.html), [XrHapticVibration](https://registry.khronos.org/OpenXR/specs/1.1/man/html/XrHapticVibration.html)). Two consequences: (i) at most you get a **scalar amplitude + duration** per hand — an extremely lossy contact proxy; (ii) to see it at all, **the runtime must be instrumented**, since the API layer sits between game and runtime.
2. **An OpenXR API layer is the right insertion point, and there is a working template.** XR-Telemetry is a Windows OpenXR layer that observes per-frame CPU/GPU segments and composites an optional overlay *without modifying frame content*, working across SteamVR/WMR/Oculus/Pimax/Varjo ([XR-Telemetry](https://github.com/mledour/XR-Telemetry)). The same hook point can log `xrApplyHapticFeedback` calls, frame timings, and pose submission — giving you both the force-event channel and the latency instrumentation from one component.
3. **Game-mod APIs are the high-bandwidth option, but per-game and fragile.** The Unreal Engine VR mod ecosystem is the most mature: UEVR-based tooling exposes live reflection over UObject/UClass/UFunction, with tools to read/write player position/health, watch arbitrary fields for deltas, snapshot-and-diff, hook any UFunction, and run Lua callbacks inside the game loop ([uevr-mcp](https://github.com/elliotttate/uevr-mcp)). A sibling project demonstrates the general shape — a *minimal injected DLL* doing state extraction and frame publishing over shared memory while a separate daemon does the heavy lifting, plus reading the final rendered frame out of a shared section ([game-mods](https://github.com/AndrewAltimit/game-mods), [FEAR2VR `grab_frame.py`](https://github.com/praydog/FEAR2VR/blob/fd1005f5/tools/grab_frame.py), [FEAR2VR memory SDK](https://github.com/praydog/FEAR2VR/blob/fd1005f5/shared/sdk/Memory.hpp)). ⚠️ These are reverse-engineering projects; the SDK notes explicitly that a wrong offset "pointed at MAPPED memory that read back plausible-looking bytes".
4. **The clean event channel exists only in open-source engines.** ViZDoom exposes `game_variables` (`HEALTH`, `POSITION_X/Y/Z`, `VIEW_HEIGHT`, etc.), per-frame reward, the depth buffer, automatic labeling of visible objects, and the actor list/map geometry, and can run headless/off-screen ([ViZDoom docs](https://vizdoom.farama.org/index.html), [paper](https://ar5iv.labs.arxiv.org/html/1605.02097), [enum reference](https://raw.githubusercontent.com/Farama-Foundation/ViZDoom/refs/heads/main/docs/api/cpp/enums.md)). A commercial VR title gives you none of this.
5. **Pixel-based inference is the game-agnostic fallback, and the prerequisites are documented.** Behavior-cloning agents trained on the player's raw pixel stream generalise across titles with minimal per-game engineering; the P2P0.1 model runs at 20 Hz on a single consumer GPU and uses an inverse-dynamics model to label unlabeled video ([P2P0.1](https://www.alphaxiv.org/abs/2508.14295)). A black-box replication benchmark shows vision-language agents recover visual appearance far more reliably than game *mechanics* — so expect pixel inference of contact events to be the weak link ([GameReplica](https://arxiv.org/abs/2609.22308)). A game-agnostic, no-memory-access, no-mod framework using screen pixels + OS input, with a reward function per game adapter, exists as a reference implementation ([PixelVisionAI](https://github.com/dennishilk/pixelvisionai)).
6. **If you do synthesise forces from inferred contact, the classical haptic-rendering recipe is what to use.** Penalty/spring models compute force `F = K·d·n` (stiffness × penetration depth × normal) and torque `τ = (c_p − g_c) × F`, with collision detection + response running at **≥1 kHz** while visuals update at 30 Hz, synchronised client–server style ([NASA haptic rendering](https://ntrs.nasa.gov/api/citations/20110023864/downloads/20110023864.pdf), [INTECH effective haptic rendering](https://cdn.intechopen.com/pdfs/26936/InTech-Effective_haptic_rendering_method_for_complex_interactions.pdf)). The more robust variant is the **virtual proxy**: a proxy object is constrained to minimise penetration, and the force emitted is a smoothed spring force from the real probe to the proxy, giving continuous (non-discontinuous) responses at edges and multi-contact ([6-DoF haptic display](http://gamma-web.iacs.umd.edu/6DHAPTICS/6dhaptics.pdf), [H-COLLIDE](http://gamma-web.iacs.umd.edu/H-COLLIDE/)). For MuJoCo, the mechanical equivalent is `mjData.xfrc_applied` / `qfrc_applied` on the hand link — but note that 1 kHz haptic rates are wildly above your 500 Hz sim step only in the sense that 500 Hz is already adequate; **the bottleneck is your ~20–90 Hz pose/game loop, not the sim**.
7. **⚠️ No prior work found** on feeding forces derived from a commercial VR game back into a physics simulator. Treat this as a genuine gap; the nearest analogues are the haptic-rendering literature above (which goes virtual→device, not game→simulator).

## 5. Latency

1. **Frame pacing in Monado is predictive, and a slow pose client will not stall the game.** `xrWaitFrame` calls `u_pa_predict()`: the composer predicts frame id, wake-up time, `out_predicted_display_time_ns` ("at what time have we predicted that pixels turn to photons"), and the display period, then sleeps until wake-up ([Monado frame pacing](https://monado.pages.freedesktop.org/monado/frame-pacing.html), [pacing API](https://monado.pages.freedesktop.org/monado/group__aux__pacing.html)). Critically, `u_pa_latched()` **"may be called multiple times for the same frame should the app be on a frame cadence that is lower than the native compositor"** — i.e. the compositor re-uses/reprojects the last submitted frame. Combined with the LOCAL-space tracking-loss rule (§2.3), this means **a slow or stalled pose client manifests as the game holding a stale pose, not as a dropped frame**. Your bridge must therefore *detect staleness* rather than expect back-pressure.
2. **`xrEndFrame` requires an accurate `displayTime` computed from `xrWaitFrame` values**; the spec states "the better the predicted display time, the less latency experienced by the user" and warns about black pull-in and motion judder from reprojection ([xrEndFrame 1.1](https://registry.khronos.org/OpenXR/specs/1.1/man/html/xrEndFrame.html)). You should read the game's submitted `predictedDisplayTime` and `predictedDisplayPeriod` to align your pose injection with the frame it will actually be used for.
3. **Measured motion-to-photon latency baselines.** Across HTC Vive / Oculus Rift / Rift S / Valve Index, mean latency at *sudden* movement onset was **21–42 ms**, functionally reduced to **2–13 ms** once motion prediction engages, with the reduction appearing within ~25–58 ms of movement onset. Method: 240 fps camera co-registering real and virtual controller movement. Frame pipeline: **simulate → render → present, each costing a frame**, with tracking data updated at the end of the simulation stage; logic reading controller pose in `Update()` incurs **an extra 1 HMD frame** ([Rivieres et al., Behav. Res. Methods, PMC10616216](https://pmc.ncbi.nlm.nih.gov/articles/PMC10616216/), [Whiterose PDF](https://eprints.whiterose.ac.uk/id/eprint/193470/3/s13428-022-01983-5.pdf)). Independently: Vive Pro 2 @90 Hz 41.7 ms; Pico 4 standalone @90 Hz 49.2 ms; wireless 90 Hz at 50 Mbps 57.6 ms rising to 80.2 ms in a noisy scene; a minimal low-level OpenXR app over USB reduced Quest 2 to ~31–32 ms, and VRChat/SteamVR appear to add 1–2 frames of buffering ([Greendayle latency measurements](https://github.com/Greendayle/VR-Motion-to-photon-latency-)).
4. **Your loop is longer than any of these, and network delay will dominate.** In XR teleoperation, profiling shows "network delay is the dominant factor in M2M latency, regardless of variations in hardware, virtual scene, or operating environment"; teleoperation error stayed <2 cm under ideal network but rose above 10 cm under realistic latency/fluctuation and never fell below 2 cm, and error grew proportionally with round-trip delay from 100 ms to 1000 ms ([TeleXR, arXiv 2506.01135](https://arxiv.org/html/2506.01135v2); [MATER, SIGMETRICS 2026](https://intra.ece.ucr.edu/~hyoseung/pdf/SIGMETRICS2026_MATER.pdf)). Mitigations documented there: timestamp-preserving variable-length input windows, dual reconstruction/extrapolation on both sides, and latency-adaptive input window sizing. Human tolerance: perceived responsiveness degrades significantly at **+200 ms**, frustration increases at **+150 ms** additional delay ([Impact of Latency on UX in Immersive Teleoperation](https://exa.ai/library/publication/8qqr80ftxns)). Packet-loss/out-of-order handling is separately documented — a dropped pose makes the robot "move to the next received pose", producing irreversible trajectory deviation ([TeleXR](https://arxiv.org/html/2506.01135v2)).
5. **Concrete end-to-end measurement harness.** XR-Telemetry logs one CSV row per OpenXR frame with `app_cpu_ns` (wait→end), `render_ns` (begin→end, excluding the runtime's begin call), `end_frame_ns` (runtime/compositor ingest, typically hundreds of µs but 1–2 ms on young runtimes), `frame_total_ns` (full cycle wall clock), `gpu_time_ns`, `headroom_pct` and `gpu_headroom_pct` against `period_ns`, with a documented computed residual `post_end_ns = frame_total_ns − wait_block_ns − pre_begin_ns − app_cpu_ns − end_frame_ns` = **time outside OpenXR calls (game sim/physics/AI/input)** ([XR-Telemetry](https://github.com/mledour/XR-Telemetry)). ⚠️ Its own stated caveat: "a passive layer only sees the OpenXR-calling thread, so neither number includes simulation the engine runs on other threads" — so for your four-stage loop (game frame → capture → decision → pose → game frame) you still need to timestamp capture and pose-injection events yourself against `os_monotonic_get_ns` (the same clock Monado uses).

## Uncertainty flags (explicit)

- **§1.8 / §3.8** — the Unitree-G1-in-Unity-VR paper I cite (`arXiv 2604.16903`) has an anomalous identifier style. **Verify before relying on it**; its clamping numbers are useful but may not be from a real publication.
- **§2.5 / §2.6** — Monado's `r_interface.h` documentation shows a 2026 NVIDIA copyright alongside Collabora's, suggesting recent upstream change. I did **not** verify whether a haptic-report or hub→client channel was added. Diff your pinned Monado revision against the published Doxygen.
- **§1.6** — the claim that RDW perceptual thresholds are irrelevant to a robot is my inference, not a literature finding.
- **§4.7** — "no prior work on game-derived forces into a simulator" is a **negative result of my search**, not proof of absence.
- **§4.2** — whether Monado's *remote driver* (as opposed to a generic API layer) can intercept `xrApplyHapticFeedback` is unverified; only a generic OpenXR API layer is demonstrated to work.
- **§1.3** — I could not retrieve latency/bandwidth numbers for WIP→humanoid command mapping beyond the 0.47 m tracking error.
- Your G1 policy's maximum stable forward speed is unknown to me; the 0.5 m/s datapoint is the only measured one, so all "match achieved to commanded" reasoning assumes the game's thumbstick velocity range is scaled to suit.
